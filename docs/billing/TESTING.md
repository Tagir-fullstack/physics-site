# Проверка ePay

## Автоматические проверки без платежей

- `node_modules/.bin/tsx scripts/test-billing.ts`: конфигурационные запреты, суммы/календарные периоды, AES-GCM и принадлежность токена, секрет callback, identity/status API, подмена суммы/валюты/invoice/terminal/account, фиктивный транспорт sandbox, один запрос при timeout, авторизация и disabled endpoints. Не обращается к банку/БД.
- `scripts/test-billing-db.ts`: настоящая локальная PostgreSQL через фиксированный Unix socket `/private/tmp/physez-billing-pg-20261027:55437`, отдельная случайная schema с удалением только этой schema. Не использует DATABASE_URL для запросов. Нужны локальные `initdb`, `pg_ctl`, `psql`; кластер изолирован, слушает только Unix socket. Выполнить `node_modules/.bin/tsx scripts/test-billing-db.ts` после запуска такого временного кластера. Тестирует миграцию, конкурентный один заказ/dispatch, повторные callback, CHARGE-only, sandbox isolation, отмену/late callback, сохранение оплаченного периода, отсутствие чужого доступа, отзыв после refund, отмену при выключенном billing. Никаких реальных bank credentials/операций.
- `npm run build`, `npm run lint`; backend отдельно проверяется TypeScript, поскольку обычный frontend build не включает API: `node_modules/.bin/tsc --noEmit --target ES2022 --module NodeNext --moduleResolution NodeNext --skipLibCheck --esModuleInterop api/account.ts`.
- `node scripts/review-billing-ui.mjs`: отдельный тестовый Chrome на порту 9252 и Vite на 5173; Clerk/account/bank ответы подменены. Проверяет desktop/mobile, отключённую оплату, неизвестные цены, разовую оплату по умолчанию, отдельные согласия, фиктивный переход к банку, отмену, return без выдачи PRO и непубликацию юридических черновиков. Не запускать на пользовательском браузерном профиле.

## Обязательная приёмка в настоящем sandbox Halyk

Не считать выполненной по локальным тестам. Использовать TEST терминал/секреты и только официальные тестовые карты на странице банка.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Разовая успешная оплата | Один заказ, CHARGE, ровно один тестовый период, cardID не сохранён, real PRO не выдан |
| Отказ/отмена формы | Доступ не выдан; проверяется конечный банковский статус; при неопределённом состоянии новый charge запрещён |
| Возврат браузера `?success=true` или чужой order UUID | Не активирует PRO; чужой заказ 404 |
| Поддельный/повторный callback | Поддельный отклонён; настоящий повторный не добавляет период |
| AUTH/VERIFIED/resultCode100 без CHARGE | Нет активации |
| Callback с другой суммой/валютой/terminal/account | Не даёт доступ; статус берётся только через банк и сверяется |
| Потеря callback/повторная проверка | Статус восстанавливается сервером без нового списания |
| Двойная кнопка/worker параллельно | Один invoice и одна отправка на период |
| Сохранение карты с согласием | Проверенный accountID соответствует Clerk ID, зашифрованный cardID, нет PAN/CVV |
| Несовпадение/отсутствие accountID/cardID | Автопродление не активируется, ручная сверка |
| Автопродление, timeout после отправки | Только сверка старой операции, без повторного charge |
| Рекуррент требует 3DS | Доступ не выдаётся до CHARGE; самостоятельный повторный charge не запускается |
| Отмена до worker/параллельно dispatch/после dispatch | До dispatch — нет charge; уже отправленный может закончиться; повторное авто не включается |
| Отключение платежей | Списания остановлены; управление/отмена и уже оплаченный production доступ сохраняются при storageReady=true |
| Полный/частичный возврат | Отзыв конкретного периода/остановка авто; частичный возврат — отдельная согласованная процедура, не неподтверждённая автоматизация |
| Исчерпан лимит runtime/недоступна БД/банк | Никакой выдачи без записи/проверки, никаких слепых повторных списаний |
| Просроченный PRO/другой пользователь | Серверные PRO API отказывают; базовые функции сохраняются |
| Чек и чек возврата | Отдельная приёмка фискального провайдера; пока НЕ реализовано |

Тестовые ключи и реквизиты карт в отчёты/скриншоты/репозиторий не включать. Полный банк roundtrip, настоящие callback, работа scheduler и чеки ещё требуют настроенной тестовой среды.


## Просмотр интерфейса без PRO и несколько аккаунтов

В меню аватара платного аккаунта есть «Посмотреть без PRO» / «Вернуть PRO». Это локальный режим просмотра: AuthContext.isPremium и hasFeature становятся false, а оплаченный доступ, платежи и серверные права остаются прежними. Личный кабинет и ручной режим Обербека учитывают его, хотя независимо запрашивают серверный доступ. Настройка хранится в sessionStorage отдельно для каждого Clerk userId в текущей вкладке и переживает обновление страницы. Рядом с аватаром отображается Basic с оранжевой обводкой или Pro с синей; в режиме просмотра без PRO — Basic. Бесплатный аккаунт не может включить себе PRO этим переключателем.

В «Сменить аккаунт» показываются только активные сессии текущего браузера; текущая отмечена галочкой. Переключение устанавливает активную сессию Clerk и перезагружает страницу, а дерево AuthProvider дополнительно привязано к userId для сброса данных предыдущего пользователя. При выходе закрывается только текущая сессия. Вход в другой аккаунт выполняется штатным Clerk SignIn, без сохранения паролей приложением.

Обязательная внешняя настройка: в Clerk Dashboard → Sessions включить Multi-session handling и сохранить. При проверке 2026-11-07 у настроенного development instance auth_config.single_session_mode=true. Эта настройка не изменена: доступный Backend SDK не предоставляет её изменения, к Dashboard доступа нет. «Добавить аккаунт» сначала проверяет публичную конфигурацию: пока single-session включён, показывает ссылку на настройку и не открывает вход, который мог бы заменить текущую сессию. После включения повторный клик открывает штатную форму входа. Конфигурация не кэшируется.

Проверено в изолированном браузерном сценарии с реальным AuthProvider и подменёнными сессиями/API: включение/возврат PRO, обновление страницы, базовые метки личного кабинета, разделение режима по аккаунтам, фильтрация истёкших сессий, переключение и перезагрузка, запрет добавления при single-session, открытие SignIn при multi-session, ширина меню 240px и мобильный экран. Реальный второй вход требует включения Multi-session handling в Dashboard.
