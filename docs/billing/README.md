# Halyk ePay — аудит и подготовленная интеграция

Состояние: 27.10.2026. Реальные платежи выключены. Хостинг, DNS, Vercel Hobby и расписания не менялись. Миграция рабочей Neon не выполнялась. Новых зависимостей нет.

## Что уже существовало

- React/Vite, Clerk, `/account`, серверная проверка Clerk JWT и ролей, Neon/Postgres + Drizzle.
- PRO в защищённых Clerk public/private metadata, администраторские исключения, проверки `hasPremiumAccess` для API преподавателя/тестов/загрузок и отдельные проверки лабораторных.
- `paymentsEnabled:false`, интерфейсы типов подписок, но без работающих заказов, платёжного API, таблиц подписок или расписания списаний.
- `/terms` об использовании материалов и `/privacy` об обработке аккаунтов; это не комплект документов продавца для эквайринга.

## Реализация

1. `/premium` — месячный/годовой период; цена задаётся сервером, без выдуманных тарифов. Разовая оплата по умолчанию, автопродление с отдельным согласием. История, проверка платежа и отключение будущих списаний. Ссылка из существующего кабинета; отдельный аккаунт не создаётся.
2. `/api/account?billing=…` использует существующий Vercel entrypoint, Clerk и Neon. Новая функция Vercel не добавлена. Callback и worker имеют собственные проверки; все пользовательские операции проверяют Clerk, владение заказом и Bearer, изменения — также origin.
3. Две новые таблицы `billing_orders` и `billing_subscriptions`, Clerk ID — ключ владельца. Drizzle-схема и явная additive SQL-миграция. Таблиц пользователей/карт-дублей нет. SQL-транзакции и advisory locks защищают заказ, период и отмену.
4. Цена/валюта/период/terminal/accountId/номер заказа формируются сервером. Перед OAuth заказ переводится атомарно в pending. Повторная кнопка/ключ не создают вторую операцию.
5. Callback — только сигнал. Проверяется случайный секрет заказа `secret_hash` в постоянном времени по хешу; статус, сумма и cardID callback не принимаются на веру. Затем независимый authenticated status API проверяет invoice, terminal, amount, currency, transaction ID и accountID, если банк его вернул. Только `CHARGE` выдаёт период. `AUTH`, `VERIFIED`, `resultCode=100` сами по себе не означают оплату. Браузерный return ничего не активирует.
6. cardID сохраняется лишь из проверенного статуса банка при точном accountID владельца и согласии на рекуррент. AES-256-GCM, отдельный серверный ключ, AAD Clerk ID. PAN/CVV/mask, тело bank response, секреты и auth token в базу/логи не пишутся. Нет формы ввода карты на Physez.
7. Worker создаёт один заказ на период и один раз атомарно резервирует отправку. При timeout/crash/3DS — только сверка, без автоматического повторного списания. Отмена увеличивает cancel_version, выключает autorenew, удаляет локальный cardID; старый callback не может включить его обратно. Уже отправленная операция может завершиться, это указано пользователю.
8. Доступ считается по подтверждённым production-периодам. Sandbox не открывает настоящий PRO. Отмена сохраняет оплаченный период. Проверенный REFUND отзывает соответствующий период и отменяет продление. Worker проверяет и активные оплаченные заказы для обнаружения возвратов; интерфейс ручных возвратов и reKassa ещё не интегрированы.
9. Существующие ручные PRO и администраторы сохраняются. AuthContext получает платный доступ с сервера, обновляет при фокусе, раз в минуту и после проверки оплаты; API проверяет доступ при каждом защищённом запросе. Браузерное скрытие панели само по себе не является защитой: уже поставляемые клиентские формулы/симуляции остаются клиентским кодом, их нельзя сделать секретными оплатой. Защищённые данные/сервисы проверяются на сервере.

## Подготовка sandbox

1. Заполнить серверные переменные по `.env.billing.example`, отдельные TEST credentials Halyk, тестовые цены; настоящие live credentials не использовать. Предпочтительно отдельная тестовая Neon branch, отдельный Clerk test tenant, отдельные ключи шифрования. Sandbox и production имеют отдельные строки и endpoint allowlist, но физическую изоляцию окружений всё равно необходимо настроить.
2. Просмотреть `scripts/sql/billing-epay.sql`, сделать snapshot и применить к выбранной тестовой базе: `BILLING_MIGRATION_APPROVED=true node --env-file=.env.local scripts/setup-billing.mjs`. Скрипт не запускается без явного флага. Не использовать `db:push` вслепую.
3. Установить `BILLING_STORAGE_READY=true`, `BILLING_MODE=sandbox`. Цены — положительные целые тенге. `BILLING_RECURRING_ENABLED=true` только для отдельной проверки сохранённой карты. На этом этапе live остаётся заблокирован.
4. `EPAY_PUBLIC_ORIGIN` — существующий публичный HTTPS адрес тестового развёртывания с данным backend. Callback должен быть доступен банку; localhost для полного bank roundtrip не подходит. В этой работе развёртывание не создавалось.
5. Использовать только карты со страницы [официальных тестовых данных](https://epayment.kz/docs/Test-credentials) непосредственно на странице банка; не копировать PAN/CVV в репозиторий, логи или наши формы.
6. Пройти матрицу в `TESTING.md`, сверить реальные поля callback/status с банком. Подтвердить `accountID`, cardID и `secret_hash` именно своего терминала. При несовпадении интеграция должна отказать безопасно, а не ослаблять проверку.

## Worker и эксплуатация

`POST /api/account?billing=worker`, `Authorization: Bearer <BILLING_SCHEDULER_SECRET>`. Не вызывать из браузера и не публиковать ключ. До live — только sandbox. За один вызов максимум три сверки и одна попытка нового продления; при большом количестве подписок понадобится согласованная частота/ёмкость worker. Расписание намеренно НЕ создано: отдельно согласовать коммерческий хостинг, допустимые фоновые задачи, timeout/длительность и распределённый scheduler, затем проверить нагрузку. При потере выполнения после dispatch система не повторяет charge. Нужны мониторинг, алерты и операционная сверка перед production.

`BILLING_MODE=disabled` блокирует новые платежи и банковские обращения. При `BILLING_STORAGE_READY=true` оплаченный доступ, история и отмена production-продления продолжают работать. Не выключать storageReady ради остановки списаний: этим скрываются платежные права и управление. Сначала выключить recurring или mode; существующие банковские операции могут завершиться. После восстановления режима сверить незавершённые заказы.

Не создавать новый invoice для неизвестной операции. `102/not found`, `107`, timeout не считаются доказательством отсутствия будущего списания. Незавершённый checkout без оплаты пока блокирует следующий заказ: оператор должен подтвердить у банка окончательное отсутствие/отмену операции перед переводом в failed/cancelled. Автоматическое истечение не реализовано без согласованных гарантий банка. Это обязательный сценарий приёмки перед production.

Для `AUTH` не выдаём доступ и не делаем автоматический capture: подтвердить у Halyk одностадийную схему с финальным CHARGE либо согласовать отдельную capture-реализацию. 3DS при рекурренте сейчас требует ручного разрешения/повторного клиентского checkout после завершения старой операции, без автоматического обхода.

Ключ шифрования нельзя менять без миграции существующих cardID; план ротации/восстановления согласовать отдельно. Повторная смена callbackKey не должна лишать текущие заказы проверки: завершить/сверить их перед ротацией. Отдельный lifecycle/card-deactivation в банке по запросам удаления данных требует согласования API/прав; локальная отмена удаляет наш токен и прекращает будущие списания, не обещает удалить карту из банка.

Invoice — последовательность 100000…999999 без цикла: уникальны последние шесть цифр согласно документации. Перед исчерпанием и при восстановлении snapshot нельзя сбрасывать sequence; менеджер должен подтвердить диапазон/стратегию и отсутствие пересечений с другими системами на этом же терминале. Sandbox тоже расходует номера.

Возврат определяется по проверенному статусу REFUND, не по browser query. Частичные возвраты и пересчёт оставшихся предоплаченных периодов требуют операционной обработки/приёмки; интерфейс возвратов не обещан. При REFUND карточка может показывать историческую paidThrough, но сервер не выдаёт отозванный период. Фискальная очередь, чеки/чеки возврата и сверка с reKassa пока отсутствуют: `BILLING_FISCAL_APPROVED` не включать, пока это не реализовано либо письменно не согласована допустимая схема.

## Юридические документы и ограничения запуска

`docs/billing/legal/` содержит только непубличные проекты для владельца/юриста. `/legal/…` сейчас показывает отсутствие утверждённых документов, не черновик оферты. Для публикации заполнить реальными сведениями и утвердить каждый документ в `src/config/billingLegal.ts`, сменить draft-редакцию на окончательную, `approved=true`. Production технически не включится с пустыми документами.

Все live approvals по умолчанию false; даже корректный live secret не включает списания. Не включать их по результатам unit-тестов: требуется отдельное разрешение владельца на live.

Официальные источники (проверены 27.10.2026): [платёжная страница](https://epayment.kz/docs/platezhnaya-stranica), [сохранённая карта](https://epayment.kz/docs/platezh-po-sokhranennoi-karte), [статус транзакции](https://epayment.kz/docs/check-status-payment), [тестовые данные](https://epayment.kz/docs/Test-credentials). Требования/анкета банка прочитаны из четырёх файлов владельца в Downloads; личные документы в репозиторий не копировались.
